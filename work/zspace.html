Case 01 | 电商直播经营 Agent · 2025.11 — 2026.06

让 Agent 懂生意，而不是只会查表。

运营问“这场为什么比上一场差”，Agent 要答得出来，还要答得出处。

01Context

直播这门生意，天生不适合被复盘

一场直播里，主播的每句话、运营的每个动作（改价、上链接、发福袋、切款）都在几秒钟内发生，也在几秒钟内过去。事后留下的只有数据，没有过程。更麻烦的是它不可复现——同一套货盘、同一个主播，换一天再播，结果可能完全不同，因为流量结构变了。

所以“A 场比 B 场好”这个结论本身就不一定成立，除非你把变量控住。而一场直播卖得好不好，至少由六件事共同决定：流量、货盘、话术、时段、平台活动、竞品动作。任何一个变了，结果都会变。

直播复盘天然是一件“证据不足”的事——
你手上只有一个结果，和一堆可能的原因。

客户现在怎么复盘

下播之后，运营去平台后台导数据，拼到 Excel，看几个核心指标，和上一场比一比，得出一个说法，写进周报。这套流程有四个问题：

  • 数据是拼出来的。平台后台、ERP、投放后台、客服系统、自建埋点，五套数据五个口径，经常对不上；运营知道对不上，但没时间去查，最后默认“差不多就行”。
  • 归因靠经验。“这场流量不行”“主播状态不好”——两句话都对，但都没法验证，也没法变成下一场的动作。
  • 结论留不下来。复盘写在周报里，下一场从零开始；半年后没人记得“上次改话术到底有没有用”。
  • 人一走就断档。判断力长在操盘手脑子里，人走了，店铺的经验就没了。
02Split

十步里，只有三步交给模型

客户真正想要的不是报表，是“下一步怎么办”。所以这条 Agent 只干三件事：查数、复盘、给下一场的建议——每一件都必须能回答“凭什么”。

产品形态是一句话：用对话提问，用画布看证据。左边提问，右边跑链路，每一步的输入和输出都摊开。上面那张图就是一次完整运行。

链路长不等于复杂。
长，是因为每一步都留了痕迹。

十个节点，五种颜色

  1. 01提问入口定场次、定权限固定
  2. 02意图分型查数 / 归因 / 复盘 / 对比Agent
  3. 03信息校验缺信息就回问，不猜固定
  4. 04口径对齐摊开让人点确认人工
  5. 05语义检索口径字典 + 历史复盘检索
  6. 06取数执行只读沙箱，白名单之外看不见固定
  7. 07完整性校验数据不净就熔断固定
  8. 08分析编排复现、排除、拆解、归因Agent
  9. 09独立复核专挑口径与因果Agent
  10. 10结论画布结论 / 依据 / 待确认 / 动作交付

颜色和上面演示里的节点一致：蓝 = 固定流程，紫 = Agent，橙 = 检索，绿 = 人工确认，青 = 交付。

为什么这么切

  • 能写死的，不进模型。入口、校验、取数、复核、画布这五步，逻辑是确定的。写进代码，结果就是可复现的；交给模型，同样的输入今天和明天可能不是一个答案——对复盘工具来说，这比慢更致命。
  • 模型只做“信息不全时的判断”。意图分型、归因编排、独立复核，这三步的共同点是：规则写不出来，但人做得出来。模型的活是给出一个可被检查的假设，不是执行一个确定的动作。
  • 人只出现在会改变结论的地方。十步里只有“口径对齐”必须由人点。因为口径错了，后面八步算得再准都是在算错的东西——这是整条链路唯一没人能替代的那一下。

这个比例不是设计出来的，是逼出来的。第一版我们把取数和校验也交给模型“灵活处理”，结果出现了查错表、时间窗错位、拿 3 场样本下结论这类问题。后来一条条挪回固定流程，模型的地盘缩到三步，准确率才稳住。

所以“AI 产品”这件事在我这儿有个很具体的判断标准：不是模型用得多，而是你能不能指着链路上某一步说，这里为什么必须是模型。

03Decisions

三个我当时做下的取舍

这一节是我最想讲的——不是做了什么，而是否掉了什么。

01不做“更快的报表”

报表解决“看见”，客户要的是“下一步”。所以第一版就没做自定义看板，把力气全放在“结论能不能被追问”上。

02口径先于模型

同一个“转化率”，运营、投放、财务是三个算法。不先把定义写进字典，模型算得再快也是在算错的东西。

03结论必须分级

事实、推断、建议分开标注，超出数据支持范围的结论直接不输出。宁可少说，不能说错。

为什么口径这件事只能产品经理来做

工程师能建表，算法能查数，但“这个词在客户嘴里是什么意思”只有做过业务的人知道。我做的事可以一句话概括：把客户手里的表、字段、指标口径，翻译成 Agent 能理解、并且和运营说的是同一件事的“生意语言”。

指标字典不是一张字段清单，每条都必须是三要素：定义 + 时间窗 + 数据出处。缺一条，两个人在会上就能吵起来。

04Evidence

证据：口径字典、实体链、复核清单

指标字典（节选）

指标定义时间窗出处
GMV下单金额，含未支付与退款场次开始至下播 +30 分钟订单表 · 按场次 ID
成交额支付成功且未退款同上，T+1 重新结算支付流水 · 结算口径
进入率进入直播间人数 / 曝光人数按小时切分平台后台 · 曝光口径
单位时间转化效率成交单量 / 有效讲解时长按商品切分自建埋点 · 讲品事件

注：真实字典共 40+ 条，这里只放四条；数值与字段名已脱敏。

实体链：店铺 → 直播间 → 场次 → 商品 → 订单

所有查询都必须能落到这条链上，否则就是“猜”。运营问“这场为什么差”，Agent 要能一路拆到具体商品和具体时段，而不是给一个整体结论。

Bad Case 分四层，不混在一起

层典型表现怎么修
语义层口径理解错、实体指代错补字典、加同义词与追问
取数层查错表、时间窗错、权限缺数据校验、口径规则、只读通道
分析层样本不可比、因果倒置变量控制清单、复核环节
表达层结论超出数据、没出处输出约束、分级模板
05Results

结果：先把“数对不对”解决，再谈快不快

80+覆盖运营人数
2500+累计复盘场次
−72%单次复盘人工投入
中位数 90 → 25 分钟
98%数字准确率
严重错误 0 起

这四组数字里，我认为最有意义的不是“快 72%”，而是严重错误 0 起。复盘工具最怕的不是慢，是给了一个理直气壮的错答案——那会让运营在下一场做出更贵的错误决定。

数字准确率的统计口径：随机抽取复盘结论中的数字，与源表逐条核对；错误分“轻微（四舍五入、单位）”和“严重（口径错、张冠李戴）”。

06Reflection

复盘

最大的教训是：语义层做得太晚。项目前期我们在分析流程上花了很多时间，但真正卡住客户的是“你说的转化率和我说的不是一个东西”。如果重来，我会在第 2 周就把指标字典的骨架拉出来，哪怕只有 10 条。

第二个教训是复核环节容易被当成负担。一开始运营觉得“又要我确认一遍口径”很烦，直到有一次复核拦下了一个样本量只有 3 场的结论——从那以后，他们自己会主动看样本量。

“你怎么保证 Agent 的结论是对的？”

不能保证它对，只能保证它“可被检查”。做法是三层：口径先对齐（口径没确认就不往下走）、结论分级（事实/推断/建议分开）、每条结论带出处（哪个表、哪个时间窗、哪次查询）。剩下的靠独立复核和回归样例。

“98% 准确率是怎么算的？会不会自说自话？”

抽样核对：从复盘结论里抽数字，回源表逐条比。错误分轻微和严重两级。这个口径本身也写在文档里，客户可以按同样方法抽查。

“为什么不让 Agent 直接给动作建议？”

给过，后来收窄了。建议一旦具体到“把 A 款提到第 3 位”，运营会照做，但模型并不知道明天的流量结构。现在只给到“哪个变量最可疑、下一场怎么验证”，动作由人定。
